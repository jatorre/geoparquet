# Where the OGC wording differs from `geoparquet.md` (and why)

**Status: PROPOSAL for SWG review.** This file lets reviewers check that the OGC document
(`ogc/`) does not change the meaning of the community specification. Source text is
`format-specs/geoparquet.md` at tag `v2.0.0-rc.1` (identical on `main` at `21eba45`), plus the
`covering` text of PR #302 for the Bounding Box Covering class. Line numbers (`L52`) refer to that
file. Crosswalk row IDs (`FM-3`, `GT-4`, …) refer to [`crosswalk.md`](crosswalk.md); spec issues
(`SI-n`) to [`spec-issues.md`](spec-issues.md).

## Global conventions

| # | Change | Why |
| --- | --- | --- |
| G1 | `MUST` → `SHALL`, `MUST NOT` → `SHALL NOT`; `SHOULD`, `MAY` unchanged. Lower-case "must" in the markdown is treated as descriptive unless the JSON Schema enforces it (then it becomes a requirement, see per-item notes). | OGC Policy Directive 49 / ISO Directives Part 2 prescribe SHALL. Stated in Clause 5 (Conventions). |
| G2 | JSON "field" / "key" → "member"; "Parquet logical-type `crs` property" → "`crs` parameter of the `GEOMETRY`/`GEOGRAPHY` logical type". | JSON (RFC 8259) terminology; "type parameter" is what `LogicalTypes.md` calls `crs` and `algorithm`. |
| G3 | Normative keywords appear only inside requirement / recommendation / permission blocks. The surrounding prose, copied from the markdown, is rewritten in the indicative ("Geometry columns are at the root of the schema"). | OGC ModSpec: provisions live in the boxes; prose must not carry competing normative statements. No sentence was dropped; each keyword sentence has a block. |
| G4 | Conditions that the markdown states in surrounding prose ("If no value is set, no assertions are made…") are written into the requirement ("If the `orientation` member is present, …"). | Makes each requirement testable on its own; fixes the unconditional wording of PR #224 R7. |
| G5 | Statements addressed to software (readers, implementations) are not requirements. They are reproduced verbatim in meaning in Clause 8 (informative). Affected: L93 reader MUST/SHOULD on `crs` forms (CRS-8, CRS-9); L263 forward-compatibility MUST (VC-1); L278–L279 SHOULD NOT / SHOULD (VC-2, VC-3). | SWG decision (chair, 2026-09-03): a single standardization target, the file, is simpler and easier to get approved. **This is the one place where the OGC document is deliberately weaker than the markdown: two MUSTs and three SHOULDs on readers are not testable requirements.** |
| G6 | The Bounding Box Covering class (Clause 7) is taken from PR #302, not from the rc.1 text. | The chair expects #302 to merge; the clause is marked conditional in an editorial comment and can be removed as a unit. |
| G7 | Normative references to Apache Parquet are pinned to format version 2.12.0 (`LogicalTypes.md`, `Geospatial.md`), the version the markdown links. | Dated references are required for normative use. See SI-9 for a version problem in one of those links. |
| G8 | Terms and definitions (Clause 4) are new: bounding box column, column metadata object, covering, geometry column, GeoParquet file, GeoParquet metadata, primary geometry column, WKB; CRS, dynamic CRS and epoch from ISO 19111. | OGC template requirement. Definitions were written to match how the markdown uses the words. |

## Requirements Class Core

| Identifier | Source | Difference | Why |
| --- | --- | --- | --- |
| (no requirement) Parquet file, Clause 6.2 | Overview (L5), implicit | Prose plus a NOTE: "a GeoParquet file is an Apache Parquet file" is stated as the premise of the clause, **not** as a requirement, because the markdown never states it as a MUST. An earlier draft had it as /req/core/parquet-file; removed so the OGC text stays purely derivative (SI-22). | Every other requirement presupposes it; the normative reference to Parquet is anchored by /req/core/geometry-column-type and /req/core/wkb instead. |
| /req/core/geo-metadata | L32 | Part C pins the schema to "the GeoParquet metadata JSON Schema for version 2.0.0". | The markdown links the relative `schema.json`; a Standard needs a dated artefact. The `v2.0.0` release URL exists only once 2.0.0 is tagged. |
| /req/core/file-metadata | L36–L40 table; `schema.json` | A: "version … SHALL be the string `\"2.0.0\"`" (markdown: "version identifier"; schema: `const`). B: "non-empty string" (schema `minLength: 1`). C: "at least one member" (schema `minProperties: 1`). That `primary_column` names a member of `columns` is a NOTE (derived from /req/core/column-metadata), **not** a part of the requirement. | A–C make schema constraints visible in prose (the schema is already normative through /req/core/geo-metadata, so this adds nothing testable). The `primary_column` rule is implied, not stated, in the markdown (FM-3, SI-2); GPQ, GDAL, the test corpus and PR #247 all treat it as a MUST. An earlier draft had it as part D; removed to stay derivative. |
| /req/core/column-metadata | L40, L46 | Two parts (every geometry column is described; each member is an object with `encoding` and `geometry_types`). The reverse direction, "every member name of `columns` is the name of an existing column", is a NOTE, **not** a requirement, because the markdown only describes it ("Each key is the name of a geometry column in the table"). | Both validators fail a file whose `columns` names a non-existent column (CM-1 reverse direction, SI-4). An earlier draft had it as part B; removed to stay derivative, proposed to the community instead. |
| /req/core/geometry-column-type | L15, L50, L114 | Merges three sentences (logical type; `encoding` "Only WKB"; BYTE_ARRAY + logical type) into one two-part requirement. | Same statement made in three places. |
| /req/core/geometry-column-nesting | L19 | "SHALL be at the root of the Parquet schema (that is, it is not contained in a group field such as a struct, list or map)." The parenthesis restates the markdown's "In practice, this means…" sentence as an explanation, not as a second SHALL. The 1.1 sentence "A geometry MUST NOT be a group field" is **not** restored. | 2.0 text; PR #234 removed the group-field sentence (GC-3). With a logical type a geometry column is necessarily a primitive column anyway. |
| /req/core/geometry-column-repetition | L23 | None (two parts). | |
| /req/core/wkb | L15, L112 | "Each non-null value … SHALL be a geometry encoded in WKB as specified for the `GEOMETRY` and `GEOGRAPHY` logical types in [Parquet Geospatial]". The markdown says the logical types "annotate a BYTE_ARRAY that encodes geospatial features in the WKB format". | Makes the per-value obligation explicit and delegates the WKB variant to Parquet, as the markdown does ("provide full details on implementing the encoding"). |
| /req/core/axis-order | L118 | Markdown has no keyword ("is therefore always (x, y)"). Written as SHALL, for (x, y) only, by reference to the identical Parquet rule. Nothing is said about the position of Z and M, because neither the markdown nor Parquet's axis-order text says anything about them. | It is a hard constraint that every validator heuristically relies on (AX-1); Parquet states it for the logical types, so the SHALL adds nothing beyond Parquet. |
| /req/core/geometry-types | L51, L122–L136 | A vocabulary and suffixes: unchanged. B uniqueness: markdown lower-case "must"; schema `uniqueItems`. C: "It is expected that this field is strictly correct" (L133) → "SHALL contain the geometry type, including the dimension suffix, of every non-null geometry". D: "These MUST match the corresponding Geospatial Types in the Parquet statistics" (L135) → conditioned on "where the column chunks … carry `GeospatialStatistics`", and "correspond" instead of "match". | C is the most-tested rule of the whole spec (GPQ, GDAL, four corpus fixtures) but is not phrased with RFC 2119 (GT-4, SI-7). D: Parquet statistics are optional, so an unconditional MUST is unsatisfiable when absent; names must be mapped to WKB integer codes, hence "correspond". |
| /req/core/crs-projjson | L52, L64, L89, L95 | "present and not `null`" made explicit. | L64 says "when given"; L72 allows `null`. |
| /req/core/crs-default | L52, L66 | "coordinates … SHALL be longitude and latitude based on the WGS 84 datum, that is, the CRS SHALL be OGC:CRS84". Merges "MUST use longitude, latitude based on the WGS84 datum" and "the default value is OGC:CRS84 for CRS-aware implementations". | Same fact stated for two audiences. Not machine-testable beyond range heuristics (CRS-3). |
| /req/core/crs-consistency | L52, L74, L95, table L97–L102 | One statement covering all four rows of the table: same CRS, defaults applied when absent/unset, "or SHALL both indicate undefined or unknown" for `null` / `srid:0`. The markdown says "MUST describe the same CRS" and "MUST NOT describe different coordinate reference systems". | The "both undefined" branch is the table's fourth row (CRS-4, CRS-5). Whether an absent `crs` member must agree with an unset Parquet parameter is only implied by the table's first row; made explicit. |
| /req/core/epoch | L56, L106–L108 | "SHALL be a number expressing, as a decimal year, the coordinate epoch at which the coordinates … are valid". No SHALL that `epoch` is only used with a dynamic CRS, and PR #224's R6 ("coordinates SHALL always be qualified with the epoch") is dropped. | The markdown's only constraints are the type (schema) and the semantics; "must always be qualified" is background (EP-1, SI-10). The dynamic-CRS context is a NOTE. |
| /req/core/orientation-value | L53, L140 | Table "If present must be counterclockwise" (lower-case) + schema `const` → SHALL. | Schema-enforced; separate from the ring rule so the metadata check and the data check are distinct tests. |
| /req/core/orientation-rings | L140–L142 | Condition "If the `orientation` member is present" added (G4); otherwise the markdown sentence verbatim ("all vertices of exterior polygon rings … all vertices of interior rings"). The abstract test, not the requirement, spells out that this includes Polygons inside MultiPolygon and GeometryCollection values. | "All … polygon rings" already covers polygons within multi-geometries; saying so in the test closes a gap in GPQ, which checks top-level Polygons only (OR-2), without adding words to the provision. |
| /req/core/edges-value | L54, L150–L178 | Table "Must be one of" (lower-case) + schema `enum` → SHALL. Default `"planar"` stays prose. | Schema-enforced. |
| /req/core/bbox-array | L55, L186–L194; schema | A: 4/6/8 elements with their order (schema `oneOf`; markdown list). B: geographic CRS ordering "most southwesterly … followed by … most northeasterly … as specified in RFC 7946 section 5" is made part of the requirement although the markdown sentence has no keyword. | The MUST at L186 ("MUST be encoded with an array representing the range of values for each dimension") is immediately explained by the two ordering sentences; they are the definition of "encoded". |
| /req/core/bbox-extent | L186 | "SHALL represent the range of coordinate values, in each dimension, of all non-null geometries in the geometry column". | Makes the containment property (GPQ `GeometryBounds`, corpus `bbox-does-not-contain-geometry`) an explicit test target (BB-3). |
| /req/core/bbox-crs | L196 | None. | |
| /req/core/media-type | L287 | None. | |
| /rec/core/wkb-iso | L112 | Cites OGC 06-103r4 (Simple Feature Access Part 1, version 1.2.1). The markdown links `portal.ogc.org/files/?artifact_id=18241`, which is OGC 06-103r3 (version 1.2.0). Parquet `Geospatial.md` cites 1.2.1 (artifact 25355). (2.0 already dropped the 1.1 "[1001,1007]" code range; so does this document.) | The WKB representation is the same in both editions; a Standard should cite the current edition and the one its normative reference (Parquet) uses. Flagged as SI-23 so the markdown link can be updated. |

## Requirements Class Bounding Box Covering (PR #302 text)

| Identifier | Source | Difference | Why |
| --- | --- | --- | --- |
| /req/covering/keys | covering §; schema `covering.required: [bbox]` | A: "keys … MUST be a supported encoding" → SHALL. B: "SHALL contain a `bbox` member" **added from the schema**; the markdown only says "the only supported encoding is bbox". | Schema is normative; a `covering` without `bbox` fails validation today (COV-1). |
| /req/covering/bbox-paths | bbox covering encoding § | A restates the JSON shape (also schema). B "second item MUST be xmin, ymin, etc." C "All values MUST use the same column name". D "MUST exist … and meet the criteria in the Bounding Box Column definition", spelled out as the four bbox-column requirements. | None beyond structure; D lists the requirements it points to so the test is unambiguous. |
| /req/covering/bbox-column-structure | Bounding Box Columns § | "If zmin is present then zmax MUST be present and vice versa" → "`zmin` SHALL be present if and only if `zmax` is present". | Same meaning, shorter. |
| /req/covering/bbox-column-type | idem | None. | |
| /req/covering/bbox-column-repetition | idem | "A row MUST contain a bounding box value if and only if the row contains a geometry value" kept; the following sentence ("In cases where the geometry is optional and a row does not contain a geometry value, the row MUST NOT contain a bounding box value") is not repeated. | It is the "only if" half of the previous sentence. |
| /req/covering/bbox-column-nesting | idem | None. | |
| (no requirement) bounding box column values, Clause 7.4 | bbox covering encoding §, Bounding Box Columns § | Prose plus a NOTE: the values of a bounding box column are described ("the bounding box of the geometry in the same row"), **not** required, because the markdown describes this ("captures … the bounding box of the geometry for every row"; "the values follow the GeoJSON specification") without a keyword. An earlier draft had /req/covering/bbox-column-values; removed to stay derivative. | Consequence, recorded as SI-16: the class constrains only the schema of the column, not its content, so a covering with wrong values conforms until the community adds a MUST. |

## Prose that was moved or condensed

* L5 Overview, L15, L19, L23, L27–L32, L42, L46, L60–L102 (CRS), L106–L108, L112–L118, L122–L136, L140–L196, L202: kept in Clause 6 with keywords removed (G3) and "field" → "member" (G2). The CRS narrative was reordered so that each paragraph precedes the requirement it introduces; no sentence was dropped except the duplicate restatements at L89 and L95 (covered by /req/core/crs-projjson and /req/core/crs-consistency).
* L62 "(Writing that metadata is itself optional — a writer MAY emit only the native Parquet geospatial types — …)" and L89 "Such a file is not conformant GeoParquet 2.0": moved to a NOTE in Clause 6.7 and to Clause 8.2 "Files without GeoParquet metadata". The MAY is not a permission of this Standard because a file without `geo` metadata is outside its target (it fails /req/core/geo-metadata).
* L93 reader MUST / SHOULD, L263–L279 Version Compatibility, L283 file extension rationale, L204–L259 OGC:CRS84 details: Clause 8 (informative) — see G5; the file-extension recommendation itself is /rec/core/file-extension.
* L150–L176 edge algorithm descriptions: kept as the bullet list in Clause 6.10 with the external links reduced to citations; the algorithm values are also those of Parquet's `algorithm` parameter, which is now said explicitly.
* L194 "It is not currently possible to specify M bounds without Z bounds": kept as prose.
* The column metadata table (L48–L57) gains the `covering` row from PR #302 and drops the inline MUSTs (they are the requirements).
