[[clause_distribution]]
== Requirements Class Cloud-Optimized Distribution

////
This requirements class is the "profile" suggested by Chris Holmes on PR #304: a citable baseline
definition of a well-distributed GeoParquet file, so that downstream specifications (Portolan,
https://github.com/portolan-sdi/portolan-spec) can require "GeoParquet 2.0 conforming to the
Cloud-Optimized Distribution class" instead of restating the rules, and can evolve stricter or
more specific rules on top of it.

The statements are sourced from the Portolan specification's GeoParquet rules
(specs/portolan/formats.md, section "GeoParquet") and from format-specs/distributing-geoparquet.md.
The class has two requirements, statistics present and rows spatially ordered, and nothing else.
The best practices that an earlier draft carried as six recommendations (row group size,
compression, bounding box covering, declared bounding box column, spatial partitioning, STAC
metadata) were removed from the Standard on Matthias Mohr's proposal on PR #304 (2026-09-08,
agreed by Javier de la Torre on 2026-09-09, raised again by Joris Van den Bossche on 2026-09-21):
they are still being tuned, and a community guide can follow that tuning where a Standard cannot.
They remain in the community guide, cited here as informative. The class is optional and Core does
not depend on it. See docs/ogc/CHANGES.md, section "Requirements Class Cloud-Optimized
Distribution".
////

=== Overview

include::../requirements/requirements_class_distribution.adoc[]

Apache Parquet gives writers many options, and the defaults of most libraries are not tuned for geospatial data. The GeoParquet community has converged on a small set of practices that make a GeoParquet file efficient to distribute and to query directly from object storage without a server. This requirements class states the two practices that every well-distributed file shares, as testable requirements on a single file: keep the geospatial statistics that the Parquet `GEOMETRY` and `GEOGRAPHY` types provide, and order the rows spatially so that those statistics let a reader skip data. It is intended as a baseline: specifications that publish GeoParquet, such as Portolan, can require conformance to this class and add stricter rules of their own as the community's understanding evolves.

This requirements class is optional. It depends on the Core requirements class (<<rc_core>>) and, when a file declares a bounding box covering, on the Bounding Box Covering requirements class (<<rc_covering>>). A file that does not claim conformance to this class is still a GeoParquet file.

NOTE: The practices in this class are those that `geoparquet-io` (`gpio check`) and the Portolan validator verify. Each abstract test in <<ats_distribution>> names the corresponding tool.

=== Geospatial statistics

Parquet writes geospatial statistics for `GEOMETRY` and `GEOGRAPHY` columns (<<parquet-geospatial>>), most importantly a bounding box for each column chunk (row group). Readers use these statistics to skip, from the file footer alone, any row group whose bounding box does not intersect a query's area of interest. The statistics are optional in Parquet; a well-distributed file has them for every row group.

include::../requirements/distribution/req_geospatial-statistics.adoc[]

=== Spatial ordering

Row-group statistics only help when the rows of the file are spatially ordered, so that each row group covers a compact part of the extent and a query touches few of them. GeoParquet does not prescribe an ordering method: Hilbert curve, GeoHash, S2 or R-tree based orderings all work. The requirement is stated on the outcome, the pruning that the row-group bounding boxes allow, not on a particular ordering.

include::../requirements/distribution/req_spatial-order.adoc[]

NOTE: How much pruning counts as "most" depends on the number of row groups: two row groups can never let a reader skip more than about half of the file, while several hundred well-ordered row groups let it skip nearly all of them. The executable test therefore compares the pruning a file achieves with the pruning an ideal tiling into the same number of row groups would achieve, and the threshold is maintained in the test suite rather than in this Standard, because the community is still refining it (Portolan specification and `geoparquet-io`, 2026).

=== Other distribution practices

This requirements class does not state requirements or recommendations on row group size, compression, the use of a bounding box covering, the spatial partitioning of a dataset into files, or accompanying STAC metadata. The GeoParquet community publishes its current guidance on these practices in its distribution best practices guide (<<geoparquet-distribution>>), which is informative and is revised as the community's experience grows. A file can conform to this class without following that guidance.
